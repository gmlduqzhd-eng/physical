# 현재 운영 안내 (2026-11-09)

이 문서가 현재 운영 기준이다. 기존 문서의 날짜가 붙은 시험·배포 기록은 당시 상태이며 현재 기능 목록을 대신하지 않는다.

## Google 가입과 홈페이지 회원 관리

- 메인: https://physical-pi.vercel.app/teacher/manage
- 관리자 회원 목록: https://physical-pi.vercel.app/teacher/members
- 별도 AI 도구: https://physical-teacher-studio.vercel.app/
- 교사 이용 확인 후 `Google로 가입·로그인`을 누른다. Google 계정이면 별도 가입 승인 없이 회원으로 연결된다. 앱 비밀번호와 가입 확인 메일용 SMTP는 사용하지 않는다.
- Google OAuth를 PKCE로 연결하고, 서버에서 Supabase가 검증한 사용자와 실제 Google identity를 확인한다. 사용자가 수정할 수 있는 user_metadata로 역할을 정하지 않는다.
- 최초 관리자는 프로젝트 관리자가 지정한 **정확한 이메일의 확인된 Google 계정**만 연결된다. 지정 이메일은 소스에 넣지 않는다. 다른 Google 회원은 기본 회원이며 관리자 권한을 스스로 만들 수 없다.
- 홈페이지의 `회원 관리` 탭은 관리자 계정에만 보인다. 관리자는 이메일 검색·페이지 이동으로 회원 이메일, 가입일, 최근 로그인, 이용 상태를 확인한다. 일반 회원과 학생·미인증 사용자의 목록 조회는 DB에서 거절된다.
- 가입은 자동이며 승인 대기 단계는 없다. 관리자는 필요한 계정의 사용을 제한하거나 제한을 해제할 수 있다. 재로그인해도 사용 제한은 자동 해제되지 않는다. 마지막 관리자는 제한할 수 없다.
- 메인의 Supabase 인증 토큰은 해당 탭에 보관한다. AI 도구의 독립 Auth 클라이언트는 일회성 PKCE verifier만 탭에 보관하고 Google/Supabase 사용자 프로필·액세스/갱신 토큰을 브라우저 저장소에 넣지 않는다. 서버에는 별도 서명 쿠키를 사용한다. 회원 이메일·Google 프로필은 AI로 보내지 않는다.
- 기존 공유 코드는 전환 기간에 유지한다. 기존 익명 교사 기기와 Google 회원의 소유자는 다르므로 **전환 전에 수업 복구키를 보관**한다. 계정에서는 복구키로 가져온다.
- 전환 후 관리자는 `공유 코드 사용 종료`로 기존 공유 코드 세션과 DB 익명 교사 허가를 함께 거절할 수 있다. 종료 전에는 코드를 아는 사람이 별도로 인증할 수 있다.

### OAuth 설정

별도 Google Cloud OAuth 프로젝트/웹 클라이언트를 사용한다. Google에는 Supabase의 고정 콜백 `https://tjrrtgdhtjdkofwqnxnz.supabase.co/auth/v1/callback`을 등록한다. Google Cloud의 외부 사용자/게시 상태가 테스트 사용자 전용이면 일반 Google 계정 가입이 제한되므로 실제 공개 설정을 확인해야 한다.

Supabase에는 메인 `/teacher/google-callback`과 별도 교사 `/google-callback`의 운영 주소 및 시험할 로컬 주소를 정확히 허용한다. 기존 다른 앱의 Site URL은 유지한다. Google 클라이언트 비밀은 Supabase 제공자 설정에만 저장하며 프론트엔드·채팅·Git에 넣지 않는다. 공개 OAuth 설정 API에는 브라우저용 publishable key만 제공하며 서버 비밀키가 아니다. 실제 Google 콘솔·Supabase 활성화와 로그인 결과는 최종 검증 보고서에 기록한다. Google 로그인으로 이동할 때에는 허용 목록 검사를 통과한 공개 수업 조건·현재 단계만 같은 탭에 최대 10분 임시 보관하고 복귀 시 삭제한다. 초안·개인별 다음 도전 기록·메모 원문·학생 정보는 복원 저장 대상이 아니다. 복귀 후 전송 동의와 채택은 다시 확인하며 자동 생성하지 않는다.

[Google 로그인 안내](https://supabase.com/docs/guides/auth/social-sign-in/auth-google) · [PKCE 흐름](https://supabase.com/docs/guides/auth/sessions/pkce-flow)

## 수업방 7일 보관과 즉시 삭제

- 수업이 종료 상태로 바뀔 때 실제 종료·보관 시작 시각을 기록한다.
- 종료 후 7일이 지난 방은 매시간 17분에 실행되는 `physical-classroom-retention` 작업에서 삭제한다. 실제 삭제는 기준 시각보다 최대 약 1시간 늦을 수 있고, 작업 장애 시 더 늦어질 수 있다.
- 현재 유효한 학생·전광판 권한이 남아 있는 방은 자동 삭제에서 제외한다. 진행·대기 중인 방과 소유자 없는 이전 방은 자동 삭제하지 않는다.
- 이전에 종료되었지만 종료 시각을 기록하지 않은 소유자 있는 방에는 이번 적용 시각부터 7일 유예를 부여했다. 과거 실제 종료 시각을 추정해 기록하지 않았다.
- 소유 교사는 자기 방만, 관리자는 전체 방을 즉시 삭제할 수 있다. 방 이름을 정확히 입력해야 삭제된다. 진행 중인 방도 삭제할 수 있으며 복구 기능은 없다.
- 방 삭제는 모둠 결과·점수 검토·관련 참여/초대/복구 권한을 함께 제거한다. 재사용 활동 템플릿과 내려받은 파일은 별도다.
- 만료 회원·관람·교사 허가·입장 실패 횟수·임대 행도 정리한다. 정리 실행 기록은 개인 식별자 없이 건수·시각을 30일 보관한다. 관리자는 미리보기와 최근 실행 결과를 확인한다.
- **공유 Supabase 프로젝트의 Auth 계정 자체는 자동 삭제하지 않는다.** 다른 앱의 인증·자료와 연결될 수 있으므로 프로젝트 관리자가 별도로 관계를 확인하고 정리해야 한다. 전체 익명 계정을 생성 시각만으로 삭제하지 않는다.

## 점수 검토

새 방은 게임 점수에 교사 확인을 기본 적용한다. 기존 방은 이전 동작을 유지하며 소유 교사가 점수 확인을 켤 수 있다. 교사 화면과 상세 제어 패널에 `게임 점수 확인`이 있다.

- 학생의 기존 점수 직접 변경 RPC는 확인 방식 방에서 거절된다.
- 학생은 소속·진행 상태·교사가 설정한 점수 상한 안에서 검토 요청을 보낸다. 기본 상한은 한 번에 10,000점이다. 이는 활동 효과나 안전 기준이 아니다.
- 같은 제출 ID의 재전송은 재사용하고, 같은 학생·모둠·활동의 승인 대기 중복은 하나로 합친다. 학생당 분당 새 요청 3개, 모둠당 대기 30개로 제한한다.
- 교사는 점수를 수정해 반영하거나 반영하지 않을 수 있다. 승인 중복 클릭은 두 번 더하지 않는다. 종료한 수업에는 점수를 승인하지 않는다.
- 기존 미션의 서버 계산 점수와 게임 점수 검토는 별개다. 학생 화면은 제출과 승인 후 반영을 구분한다.
- 교사 확인을 끈 이전 방식과 일부 기존 이벤트는 학생 기기의 신고값을 사용한다. 실제 운동이나 부정행위 방지의 증거로 사용하지 않는다.

## 공용 기기와 AI

학생 프로필·인증 토큰뿐 아니라 완료·회고 확인과 점수 재전송 정보도 **현재 탭 세션, 최대 8시간**으로 정리했다. 이전 버전의 영구 저장 확인/대기 정보는 읽을 때 제거하며 다른 학생 정보로 이관하지 않는다. 만료 확인은 접근 시 수행한다. 탭을 닫기 전에 저장 완료를 확인한다. 네트워크 로그아웃이 실패해도 해당 탭의 로컬 삭제는 수행한다. 다른 열린 탭과 내려받은 파일은 직접 정리한다.

AI에 학생 기록·실명·번호·별명·얼굴·연락처를 보내지 않는다. 다음 도전은 로컬 규칙이며 AI라고 표시하지 않는다. AI 초안의 원문 참조·형식·시간 합 검사는 교육적 타당성 전체를 보장하지 않는다. 교사가 수정·채택한다.

AI 도구의 `전체 교사 도구 사용량·대기 안내`에서 일일 요청 수와 처리 중 상태를 확인한다. 429의 Retry-After 동안 생성 버튼을 제한하며 자동으로 다시 생성하지 않는다. `생성 응답 기다리기 중단`은 브라우저의 대기를 멈추는 기능으로 이미 접수된 서버 처리를 취소하거나 사용량을 되돌리지 않는다.

전역 제한은 동시 1개·분당 3요청·한국 날짜당 100요청이다. 실패한 요청을 포함하며 요청 내부 모델 호출은 최대 3회다. 요청 수를 금액 상한으로 해석하지 않는다. 제공자의 학습·로그·보관 조건과 학교 승인 절차는 별도로 확인한다.

## 활동 자료 점검

관리자는 안전 안내·학년/참여 방식·교육과정 근거를 실제로 확인한 뒤 체크 항목만 기록한다. 활동 목록의 규칙 상세에 점검 기록을 표시하며 교사 신원은 공개하지 않는다. 원자료 SHA256이 현재 자료와 다르면 이전 점검을 현재 자료에 적용하지 않는다. 점검 기록은 공인 인증·현장 안전 판정·실제 수업 효과 검증을 뜻하지 않는다. 아직 검토하지 않은 자료를 일괄 승인하지 않았다.

## 실행·검증·배포

```sh
npm ci
npm run dev -- --host 127.0.0.1 --port 5173 --strictPort
npm run dev:api
npm run dev:studio
npm run dev:studio:api
npm run verify:release
npm run healthcheck
```

개발 서버는 별도 터미널에서 실행한다. 메인 API는 8787, 교사 AI API는 8788이다. 필요한 환경 변수는 기존 `.env.example`을 따른다. 계정 인증은 기존 Supabase URL·publishable key 및 서버 전용 bootstrap/AI 제한 비밀을 재사용하며 새 비밀을 프론트엔드에 추가하지 않았다.

- `Application checks`: main push와 PR에서 린트·서버 타입 검사·회귀 검사·두 앱 빌드를 실행한다. 기존 Vercel 메인 자동 배포와 병렬이며 배포 차단을 보장하지 않는다. 강제 승인 절차가 필요하면 GitHub 보호 브랜치와 Vercel 배포 검사를 설정해야 한다.
- `Production connectivity`: 30분 간격으로 두 앱과 DB/제한 서버 준비 API를 조회한다. 인증 정보·학생 자료·실제 AI 호출은 사용하지 않는다. GitHub 실행 지연과 실패 알림은 해당 계정의 알림 설정을 따른다.
- `Release teacher studio`: main에서 수동 실행해 검사→허용 목록 준비→Production staged 배포→준비 API 확인→승격한다. GitHub의 `teacher-production` 환경에 **VERCEL_TOKEN**과 승인 규칙을 직접 설정해야 한다. 현재 토큰을 GitHub로 복사하지 않았다. 비밀은 출력하거나 실행 인자로 넣지 않는다.
- 별도 교사 프로젝트를 일반 저장소 push만으로 갱신하지 않는다. 현재 작업의 배포는 기존 인증된 CLI 절차로 수행한다.
- 서버 로그에는 정해진 이벤트 이름·상태 코드·소요 시간만 추가했다. Google 회원 정보·입력·초안·토큰을 로깅하지 않는다. 플랫폼 자체 요청 로그는 제공자 정책에 따른다.

## 현장 검증

`/device-check`에서 연결을 시험하고 수업 현장 체크를 할 수 있다. 확인 결과는 화면 메모리에만 있다. 카메라·센서 API 존재 여부는 실제 센서 정확도 확인이 아니다.

브라우저 폭 검사·합성 SQL/HTTP 시험과 실제 스마트폰·태블릿·학교 Wi-Fi·학생 활동 시험을 구분한다. 후자는 사람이 기기와 수업 공간에서 수행해야 하며 이번 코드 검사만으로 완료 표시하지 않는다. 대표 수업에서 QR 입장, 예정 인원 동시 접속, 저장·재접속, 도움 요청, 대체 동작, 소리 전달, 공용 기기 정리를 먼저 확인한다.

관련 없는 번역·구형 테이블의 기존 보안 경고는 이 작업으로 모두 해결되었다고 주장하지 않는다.
