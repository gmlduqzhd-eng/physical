# 수업방 접근 권한과 운영 안내

2026-10-20. Supabase tjrrtgdhtjdkofwqnxnz의 수업방 3개 테이블과 관련 점수·미션 RPC를 실제 수정했다. 익명 인증은 사용자가 승인한 뒤 활성화했다. 실명·이메일 없는 임시 인증 ID로 방·모둠별 권한을 확인한다. 인증 ID는 가명 식별자이며, 개인정보가 전혀 없다는 의미의 완전 익명 처리를 주장하지 않는다.

## 수업 진행

1. 교사는 기존 12자 이상 접근 코드로 교사 화면에 로그인하고 방을 새로 만든다.
2. 학생에게 해당 모둠만의 4자리 PIN 또는 모둠 QR을 안내한다. 학생은 PIN 또는 QR 입장 모두에서 학생 번호(1~99)와 별명(2~12자)을 입력한다. 모둠 QR에는 기존 12자리 참여 코드가 포함된다.
3. TV는 별도의 16자리 읽기 전용 코드로 입장한다. 교사 기기의 TV 열기 버튼도 읽기 전용 권한을 발급한다.
4. 기기를 바꾸거나 탭을 닫기 전 교사 화면의 복구키를 별도로 보관한다. 새 기기에서는 교사 인증·8자리 복구용 수업 PIN·32자리 복구키가 모두 있어야 소유권을 복구한다. 복구하면 기존 QR 참여 코드·TV 코드·복구키를 교체하고 이전 참여 권한을 취소하므로 새 QR을 안내한다.
5. 수업 종료 후 기존 참가자·TV는 만료 전까지 결과만 볼 수 있다. 학생 점수 쓰기는 종료 상태에서 거절한다. 공용 키오스크는 여러 모둠 점수를 기록하므로 교사 인증을 거친 기기에서만 운영한다.

기존 소유자 정보가 없던 17개 방은 삭제하지 않고 잠갔다. 이전 PIN만으로 임의 소유권을 가져오는 통로는 만들지 않았다. 해당 방을 이전하려면 프로젝트 관리자가 실제 소유자를 확인하는 별도 이관이 필요하다. 기존 소유자 없는 템플릿은 인증된 교사가 읽고 새 사본으로 사용할 수 있으며 원본 수정은 차단한다.

## 허용과 거절

| 주체 | 읽기 | 쓰기 |
|---|---|---|
| 인증 전 공개 키 | 수업방·모둠·미션 템플릿 접근 거절 | 핵심 테이블과 점수 RPC 거절 |
| 참여 전 임시 인증 ID | PIN 조회의 최소 정보만 | 교사 권한·방 제어 거절 |
| 참여 학생 | 가입한 방의 모둠 공동 점수판과 배정 템플릿 | 자기 모둠의 허용된 진행 상태 및 검증된 RPC만. 다른 방·모둠 임의 쓰기와 교사 제어 거절 |
| TV 관람자 | 코드가 맞는 방의 점수판만 | 점수·보스 공격·교사 제어 거절 |
| 인증된 교사 | 자기 소유 방과 자기 템플릿 | 자기 방 생성·제어·미션 승인·초기화. 타 교사 방 거절 |

교사는 서버가 서명한 HttpOnly 쿠키를 사용한다. 서버가 Supabase JWT의 실제 사용자를 검증한 뒤 서버 전용 bootstrap 비밀로 2시간 교사 권한을 부여한다. 학생이 수정할 수 있는 user_metadata의 teacher 값은 신뢰하지 않는다. service_role 키는 브라우저나 이 연결에 사용하지 않는다.

RLS와 테이블·컬럼 권한으로 직접 점수 변경을 막고, 점수 RPC는 대상 모둠의 권한·값 범위·중복 action ID를 확인한다. 모둠 간 상점 효과는 같은 방 안에서 정해진 비용과 효과로만 처리한다. 보스 공격·미션 승인·리셋도 권한을 검사한다. 교사 타이머 처리 대표 기기는 소유권을 확인하는 DB 임대 방식으로 정한다. 공개 Realtime presence나 broadcast는 교사 권한 또는 점수의 근거로 사용하지 않는다. QR은 로컬에서 만들며 외부 QR 생성 사이트에 참여 코드를 보내지 않는다. QR 참여 비밀은 URL fragment에 넣고 읽은 뒤 주소에서 제거한다.

4자리 PIN은 진행 중인 수업의 모둠마다 고유하게 발급되고 종료된 방에는 사용할 수 없다. 잘못된 입력을 포함한 입장 시도는 임시 인증 ID마다 15분에 12회로 제한한다. 4자리 PIN은 10,000가지뿐이라 장기 비밀로 취급할 수 없으며, 다른 브라우저나 임시 인증 ID를 계속 만드는 공격까지 이 제한만으로 막을 수는 없다. PIN은 교사가 수업 중 해당 모둠에만 안내하고, 수업이 끝나면 방 상태를 종료한다.

모둠별 4자리 PIN·QR 발표 화면은 교사 복구키와 전광판 코드를 제외한 부분만 전체화면으로 연다. 입장 완료 인원은 서버 수업방 회원 행을 사용자별로 한 번만 센다. 명단은 기본적으로 접혀 있고 교사 소유권이 확인된 경우에만 RPC로 읽는다. 수업방 안에서 학생 번호가 중복되면 새 입장을 막고, 교사는 기존 번호를 해제해 기기를 잃은 학생이 다시 등록하도록 도울 수 있다. 수업 종료 시 회원 행의 번호·별명을 지우되 결과 열람에 필요한 임시 권한은 기존 만료 시각까지 남긴다. 방 삭제 시 회원 행도 함께 삭제된다.

## 환경과 마이그레이션

학생 앱의 공개 변수는 VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY이다. 비밀키와는 다른 브라우저용 publishable 키다. 서버에는 TEACHER_ACCESS_HASH, TEACHER_SESSION_SECRET, CLASSROOM_TEACHER_BOOTSTRAP, APP_ORIGIN이 필요하다. 로컬은 .env.teacher.local과 .env.classroom.local, Vercel production은 서버 환경변수로 설정했다. 실제 비밀 값은 Git·보고서에 넣지 않는다.

bootstrap은 무작위 비밀과 DB의 SHA256 해시가 일치해야 한다. 첫 마이그레이션의 안내대로 실제 서버 비밀의 해시를 physical_internal.classroom_bootstrap에 별도로 넣어야 한다. 파일만 임의로 재생성하면 연결이 끊기므로 서버와 DB를 함께 회전한다. 기존 프로젝트는 이 설정을 완료했다.

적용한 파일은 20261020013733_classroom_scoped_access.sql, 20261020015439_classroom_display_and_recovery.sql, 20261020021605_classroom_result_read_access.sql이다. 정책과 권한을 변경하기 전 합성 사용자·방으로 BEGIN/ROLLBACK 검증했다. SQL 테스트는 supabase/tests의 3개 파일이다. 기존 방이나 실제 학생 기록을 테스트 입력으로 사용하지 않았다.

학생 명단은 `20261020160000_classroom_student_roster.sql`에서 기존 회원 행에 선택 입력 칼럼을 추가해 관리한다. PIN·QR의 새 입장 함수는 번호·별명을 함께 검증하고, `(수업방, 학생 번호)` 고유 제약으로 다른 기기에서 같은 번호를 중복 등록하지 못하게 한다. 기존 회원의 빈 정보는 재입장 때 채울 수 있다. 명단 조회·번호 해제 함수는 방 소유 교사만 실행할 수 있으며, `supabase/tests/classroom_student_roster.sql`의 합성 계정 테스트는 트랜잭션을 롤백한다.

## 보관과 종료

브라우저의 임시 인증 토큰·입장 정보·개인 게임 기록은 탭 세션 저장소와 8시간 만료 검사를 사용한다. 예전 영구 저장소의 이름·기록·교사 PIN 값은 읽거나 시작할 때 제거한다. 공용 기기에서는 개인정보 화면의 지우기·로그아웃 후 다른 앱 탭도 닫는다.

DB의 교사 허가는 2시간, 학생·TV 허가는 4시간이다. 만료는 접근 거절 기준이며 DB 행 자동 삭제가 아니다. 교사 방·모둠 결과·Supabase 임시 Auth 사용자·만료된 접근 행을 일괄 자동 삭제하는 작업은 설정하지 않았다. 방 삭제는 소유 교사의 관리 작업으로 수행하며, Auth 사용자 정리는 프로젝트 관리자가 보관 정책에 따라 별도 수행한다. Supabase·Vercel 운영 로그에는 IP와 요청 메타데이터가 남을 수 있다. 해당 프로젝트 플랜별 실제 로그 보관 일수는 별도 운영 확인 항목이며 무보관으로 안내하지 않는다.

## 실제 검증

실제 HTTPS로 4개 합성 인증 주체를 만들어 27개 허용·거절 검사를 통과했다. 교사 A/B 방 분리, 잘못된 참여 코드, 가짜 교사 bootstrap, 자기 모둠 점수 저장과 중복 방지, 타 모둠 쓰기, 학생 리셋, TV 쓰기·보스 공격 차단, 소유권 복구와 예전 코드·권한 취소를 확인했다. CLI 검증용 방과 메타데이터로 구분한 합성 Auth 사용자는 정리했다. 브라우저를 포함한 임시 Auth 행의 자동 삭제는 별도 운영 정책이 필요하다.

Vercel 최종 배포에서도 서명된 교사 세션·잘못된 Origin 거절·미인증 거절·Supabase 교사 허가·소유 방 생성 흐름의 4개 검사를 통과했다. 브라우저에서는 교사 방 생성, 학생 코드 입장, 미션 10점 저장, 새로고침 후 유지, 별도 TV 입장, 수업 종료 결과 화면을 확인했다. UI 검증용 방도 삭제했으며 기존 17개 방은 보존했다.

이 통제는 방 접근 경계를 보호한다. 학생 기기에서 스스로 보고하는 점수의 실제 운동 수행 여부까지 증명하거나 완전한 부정행위 방지를 제공하지 않는다.

## 남은 운영 점검

공유 교사 코드는 교사별 개별 계정 체계를 대신하지 않는다. 서버 로그인 제한은 인스턴스 메모리 방식이므로 학교 규모 운영에는 공유 제한 저장소나 WAF, 임시 Auth 생성량 제한·CAPTCHA 정책을 함께 검토해야 한다. CAPTCHA 설정과 결제·한도 변경은 이번 작업에서 하지 않았다. 학교의 많은 기기가 같은 IP를 쓰면 Supabase 익명 로그인 생성 한도가 영향을 줄 수 있다.

보안 Advisor의 수업방 3개 테이블 익명 사용자 경고는 임시 Auth 사용자를 허용하는 조건부 정책에서도 표시된다. 현재 정책은 소유자·방·모둠·만료를 검사하며 allow-all이 아니다. private 스키마의 RLS 무정책 항목은 직접 접근을 거절하는 의도된 설정이다.

별도 번역 기능의 기존 SECURITY DEFINER 함수 경고, 현재 src/api/server에서 참조하지 않는 bomb_defusal_scores·game_controls의 기존 allow-all, 이메일 비밀번호 유출 검사 설정 경고는 이번 수업방 변경 범위 밖에 남아 있다. 프로젝트 전체의 보안 경고가 0이라고 주장하지 않는다.
